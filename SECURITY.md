# Security Policy

FlowState is a student IoT project (Team 10). This page explains what is protected, how, and what is not.

## Supported versions

| Version | Supported |
| --- | --- |
| 2.0.x (firmware `ESP32_Code/FlowState_ESP32`, `supabase/flowstate_setup.sql`) | Yes |
| 1.1.x and older (`archive/`) | No |

## Reporting a vulnerability

Please do not disclose a vulnerability publicly. Open a private advisory on GitHub
(**Security → Advisories → Report a vulnerability**) with what you found, how to reproduce it and its impact.

## What protects what

### Secrets

| Secret | Where it lives | Never |
| --- | --- | --- |
| Wi-Fi password, Supabase anon key, valve key | `secrets.h` on the team's PC (git-ignored) | in the repository, a screenshot or the report |
| Supabase `service_role` key | Supabase dashboard only | in the firmware, the website or the repository (the build refuses it) |
| Database password | Supabase dashboard and the team's password manager | anywhere public; it must be long and random, never a name or username |
| Valve key, in the browser | the open tab only (`sessionStorage`), used to sign commands | sent anywhere: only the signature leaves the page |

The anon key is public by design: it is in the website's `env.js`. What it may do is limited by the database.

### Database (Supabase)

- Row Level Security is on for both tables. The anon key may **read** and **add** rows, and never change or delete them (no UPDATE, DELETE or TRUNCATE).
- Every value is range-checked (flows 0–100 L/min, loss 0–100 %, valve 0/1, known leak levels, alert types as `A–Z 0–9 _` only, messages up to 500 characters).
- A reading whose device clock is more than 5 minutes from the server clock is stored at its arrival time, so old or future-dated rows cannot be slipped in.
- At most 60 readings and 30 alerts a minute are accepted, which limits junk data from a copied key.
- `id` is generated by the database and cannot be supplied.

**Accepted limitation:** because the anon key is public and may add rows, someone who copies it could add plausible readings,
within the limits above. Stopping that would need a per-device key, as the archived v1.1 design had, and the team's final firmware posts with the anon key.

### MQTT

- The ESP32 connects over TLS (port 8883); the dashboard over secure WebSocket (port 8884).
- The default broker is HiveMQ's **public** broker: anyone can read the telemetry topics. Readings are not secret in this project.
- **Valve commands are authenticated.** A command counts only if it carries an HMAC-SHA256 signature made with the valve key over
  `<topic root>|<action>|<timestamp ms>|<nonce>`. It must be under 5 minutes old and newer than the last accepted command, so it cannot be
  forged or replayed. The signature is compared in constant time. With the example key unchanged, all commands are refused.
- For a real home: use a private broker with a user name, a password and topic permissions per device.

### Website

- Text from the database or MQTT is always inserted as plain text, never as HTML.
- Libraries load from a CDN with Subresource Integrity hashes.
- A strict Content-Security-Policy allows scripts only from the site and jsDelivr, and connections only to the project's Supabase and the MQTT broker.
- A deployed site is fixed to the database it was built with; the Settings panel cannot point it elsewhere.
- Spreadsheet formulas in CSV downloads are neutralised.

## Known limitations

| Limitation | Effect | Fix for a real deployment |
| --- | --- | --- |
| The ESP32 does not check TLS certificates (`setInsecure()`) | A network attacker could impersonate Supabase or the broker | Pin the root certificates (`setCACert`) |
| Public broker | Anyone can read the readings | Private broker with credentials and ACLs |
| Public anon key may add rows | Plausible fake readings are possible within the limits | A per-device key checked by the database |
| Learning on the ESP32 is in RAM | A restart resets three days of learning | Save it in flash (Preferences) |

## Checklist before a demo

- [ ] The database password is long and random (Supabase → Project Settings → Database).
- [ ] `secrets.h` has a random valve key, not the example.
- [ ] Only the anon key is in `secrets.h` and in Netlify; never `service_role`.
- [ ] `KEY_CHECK` on the Serial Monitor matches the dashboard's key check.
